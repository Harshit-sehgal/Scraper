# Stable Vs Experimental

Current truth source: [`AGENT_TRUTH.md`](AGENT_TRUTH.md). Route-level evidence is generated by:

```bash
python3 scripts/generate_route_inventory.py
python3 scripts/generate_route_auth_matrix.py
python3 scripts/check_research_boundary.py
```

## Stable Product Code

Stable product code is the default path loaded with `DATAFORGE_ENABLE_EXPERIMENTAL_ROUTES=false`. It includes:

- FastAPI app setup, middleware, health/readiness, metrics, and static mount configuration in `backend/app/main.py`.
- Core jobs, results, recycle-bin, exports, URL safety, scraper diagnostics, route auth, SaaS identity/compliance, auth profiles, scheduled monitoring, and workflow routers listed in `docs/ROUTE_INVENTORY.md`.
- Central auth and authorization helpers in `backend/app/utils/rbac.py`.
- Storage/repository paths that are exercised by default quick validation.
- Frontend dashboard assets under `frontend/`, treated as internal dashboard code unless deployment docs prove otherwise.
- Validation and audit scripts under `scripts/` and `artifacts/audit/`.

Stable does not mean production-ready. It means the code is part of the default product boundary and must meet the normal auth, tenant isolation, validation, and documentation standards.

## Experimental And Research Code

Experimental code is not part of the default stable API surface. It includes:

- `backend/app/research/`
- `app.routers.experimental` routes in the generated route inventory
- Adaptive, semantic, topology, selector-memory, replay, strategy-evolution, and similar research modules unless a route or service is explicitly documented as stable with current tests

Experimental routes are gated by `DATAFORGE_ENABLE_EXPERIMENTAL_ROUTES`. The boundary is enforced by the route registry, app lifespan/mount behavior, and `scripts/check_research_boundary.py`.

## Promotion Requirements

Promote experimental code to stable only after all of the following are true:

- The route or service has a clear product use case and owner.
- Auth goes through `resolve_auth_context`, `require_principal`, `require_role`, or `require_role_with_user`.
- Tenant/user/org/project scope is explicit or documented as not applicable.
- Tests cover allowed and denied auth, tenant isolation where applicable, and expected failure behavior.
- The route inventory and auth matrix are regenerated and show no unknown auth or tenant gaps.
- Safety boundaries remain intact: no CAPTCHA bypass, anti-bot bypass, paywall bypass, login bypass, token forging, raw cookie dumping, or unauthorized/private-network scraping.
- `python3 scripts/check_research_boundary.py` passes.
- Docs explain the new stable behavior without production/SaaS overclaims.

## Future-Agent Guidance

Do not touch experimental or research modules unless the task directly targets them. Do not import research modules into stable product code to satisfy a shortcut. If a product feature needs research behavior, first create characterization tests and a promotion plan, then move the smallest stable subset through the promotion requirements above.
